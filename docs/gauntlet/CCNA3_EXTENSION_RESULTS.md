# CCNA-3 Extension — Results

Four original multi-router labs added to the labgen gauntlet, extending it from
switched campuses into routed internetworks: static/dynamic-routing scenarios,
route selection, ACL policy and asymmetric paths. They are built to test whether
TRIDENT's reasoning generalises beyond the single-router campus labs, not to fit
a known answer.

| Artefact | File |
| --- | --- |
| Lab specs, probes, offline model builder | `trident/labgen/ccna3.py` |
| Offline verification | `tests/test_ccna3.py` |
| This report | `docs/gauntlet/CCNA3_EXTENSION_RESULTS.md` |

Nothing in `spec.py`, `builder.py`, `faults.py`, `gauntlet.py`,
`broken_campus.py` or `trident/diagnostics/**` was modified. Packet Tracer was
never started. Nothing was committed by this work.

Method: every fault is derived from the spec, applied by `faulted_configs()`,
and asserted against the generated bytes. The clean control is the *intended*
configuration diagnosed by the production engine — if a healthy network produces
a finding, the lab is not shippable, because a student could not separate the
lab's faults from the engine's false positives.

## Verified offline vs needing Packet Tracer

**Verified offline (no simulator):**

* Every lab is structurally valid and scores exactly 100.
* All 21 faults apply deterministically; 16 replace a config line and 5 remove
  one, and each is proven present (or proven removed) in the generated bytes,
  including inside the decoded `.pkt` device element.
* All four `.pkt` files encode (`encode_ok=True`) and decode to the same device
  and link names.
* The intended configuration of all four labs diagnoses as **clean** (0
  findings); each fault, applied alone, produces the hypothesis kind its probe
  declares, or deliberately none.
* The ACL policy parses and binds as written (`permit`, `Gi0/1`, `out`).
* Every static route in the reference builds has its next hop on a connected
  subnet (the condition under which IOS keeps the route).

**Not verified — requires Packet Tracer 9.0.1:**

* That the file opens, that links come up green, and that interface state
  matches the config. No live session was run.
* That IOS installs the static routes and that traffic actually flows — and that
  the floating static takes over when the primary interface is shut.
* That the ACL suppresses the denied flows at runtime, and that the
  `deny ip any any` fault actually black-holes the path.
* That the probes' commands are answered by PT 9.0.1 as written. `show ip route`,
  `show ip interface brief`, `show access-lists` and `show running-config` are
  ordinary read-only commands, but the `show running-config | include ip route`
  form used by one probe is **unverified on this build**; if PT rejects the pipe,
  use plain `show running-config`.
* End-host reachability (ping from PC to PC) in either direction. No fault is on
  an end host, so nothing depends on `enterCommand` on PC-PT/Server-PT.

**Known limitations, stated rather than papered over:**

1. **No serial links.** `builder.generate()` calls `Lab.link(a, a_port, b, b_port)`
   without a `kind`, which always emits `eCopper`. A Serial interface cabled with
   copper never comes up, so the transit links are GigabitEthernet point-to-point
   /30s. The routing content is identical; only the media label differs. True
   serial links need a `kind="serial"` path in the builder, which was out of scope
   here.
2. **No default routes, and no dynamic routing protocol.** The engine's
   `MISSING_STATIC_ROUTE` detector treats a maskless static destination as `/32`
   and compares it against the dependent's `/24`, so any healthy network built on
   defaults reports itself as broken in both directions. The labs therefore use
   explicit routes to every remote subnet (the four topics are static routing,
   route selection, ACLs and asymmetric paths; OSPF/EIGRP is not part of this
   extension). A consequence: the three "route simply absent" faults
   (`route-missing-lan-c`, `route-return-missing`, `route-return-missing-r2`)
   and the two floating-static removals are **not detectable offline** — their
   probes correctly declare no hypothesis kind, and the test requires silence
   rather than inventing a claim.
3. **The ACL's deny is implicit.** An explicit `deny` bound to an interface is
   reported as `ACL_BLOCK` regardless of intent, so the clean control cannot
   contain one. The policy is permit-plus-implicit-deny; the fault is the
   explicit `deny ip any any`. This is documented in the lab brief as the
   intended CCNA-3 answer, not as a workaround the student has to guess.
4. **No `ENDHOST` faults.** `faulted_configs()` cannot rewrite `pc_ip`, so an
   end-host fault would have to ship its broken value in the intended build,
   which is the answer-key leak the spec exists to prevent. All faults are
   router config edits.
5. **Access switches are at defaults** (VLAN 1, no trunk, no SVI). These are
   routing labs; adding a VLAN layer would add detector surface without adding
   routing content, and would obscure the false-positive guard.
